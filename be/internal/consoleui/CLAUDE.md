# consoleui Package

Native Bubble Tea v2 client for server-owned `console_chat` engines. The server catalog drives the resume/new-session picker — resume rows plus brand → model → supported mode (CLI / Direct API) → effort, with Default first and labelled from the model row's `default_effort`; the mode node stamps the engine (`claude`/`codex`/`api`); models sort newest-release-first (`service.SortModelsForPicker`). Every level renders one line — `name  <muted description>`, elided to width — via `compactDelegate` (`select_delegate.go`), reused across every picker depth. On a highlighted resume row, `d` arms a two-press confirm (row detail flips to a prompt, footer advertises `d delete`/`d confirm · esc cancel`); the second `d` deletes the live chat via the injected `deleteFn` (socket `console.close` locally, `Client.Delete` — the same HTTP close route — remotely), removing the row on success or restoring it with a status message on error; `esc`/navigation/enter disarm without deleting (`select_delete.go`). A running turn renders an animated `working…` spinner at the transcript tail (tick chain starts on every idle→running transition); the main model keeps a bounded, paginated, render-cached transcript and reconciles history, live deltas/thinking, approvals, and turn state on every WebSocket reconnect. Enter submits, `y`/`n` resolves approval (`a` allows the tool for the whole session; the status bar shows the resulting `always:` list, revocable from the web UI), Ctrl+C interrupts, Ctrl+F searches, Ctrl+G enters viewport/copy mode, Ctrl+D detaches, Ctrl+X closes, and Ctrl+Y toggles per-session yolo (red `YOLO` status-bar badge while on, live via `console_chat.yolo`). At the composer's first/last line, Up/Down recall shell-style input history — seeded once — from a project-scoped aggregate across the project's console chats (`GET /api/v1/console/history`) when a project is resolved, else per-session from the current chat's tail — deduped/capped at 100, oldest→newest, and appended per send — while interior Up/Down and the `/`/`/invoke` dropdowns keep normal cursor/selection behavior; the footer shows `History <pos>/<total>` (1-based from oldest) while browsing (`input_history.go`).

Layout: transcript fills the top of the screen; a bottom status bar (engine/model, project id, connection, context%, ~$cost, `bg:N` running-workflow count, always-list) replaces the old top header — the bg count comes from `GET /api/v1/workflows/active` filtered to the chat's project, fetched on WS connect and on workflow/orchestration/delegate lifecycle events arriving over the additional project-channel subscription (`bgtasks.go`, never polled); the composer is a single-line auto-growing `textarea` (`DynamicHeight`, 1-8 rows) with a bordered "/" skill-suggestion box above it when a slash query matches, listing a reserved `invoke` directive first (completes to `/invoke `) followed by the project skills fetched once from `GET /api/v1/console/skills` on WS connect. The dropdown renders a `maxSuggestionRows`-sized scroll window that follows the selection with a `N/total · ctrl+o details` position indicator on overflow, and ctrl+o toggles a word-wrapped full-description block below it; both are folded into `chromeRows` so the transcript viewport shrinks to fit; a capped details block always ends its last line with a forced "…" marker.

`/invoke ` switches the same suggestion box to the chat's `GET .../tools` catalogue; selecting a tool runs a sequential composer-based arg prompt (per `input_schema` field, each prompt labelled with its type e.g. `queries (array, required):`) then a one-line `[i]`-inform-toggle confirm that dispatches `POST .../invoke` (transcript rows arrive over WS, no local echo). The pure state machine and schema parsing live in `invoke.go`; `array`-typed fields coerce plain-text/scalar input into a one-element JSON array (JSON arrays pass through unchanged), and confirming with invalid JSON in an `object`-typed field routes back to that field instead of dispatching.

`renderMessage` (view.go) renders every transcript category — `user_input`, `tool`/`tool_use`/`tool_result`, `thinking`, and the glamour-rendered default — through `fitWidth` (`view_wrap.go`): expand tabs to spaces, ANSI word-wrap to content width (`ansi.Wrap`, hard-wrapping unbroken long tokens), then clip any line still over width (trailing-whitespace overflow `ansi.Wrap` won't move). Printed lines must never contain tabs or exceed the terminal width — `ansi.StringWidth` counts `\t` as zero while terminals advance to the next tab stop, so either desyncs bubbletea's `insertAbove` row math and corrupts the screen. Tool rows are best-effort pretty-printed (`prettyToolContent`, JSON first then an XML token-round-trip fallback) before wrapping.

The main model renders inline (`view.AltScreen = false`, `select.go`'s short-lived resume/new-session picker stays alt-screen). Completed transcript rows are never held in model state or a viewport — they are emitted once via `tea.Println` (print.go) straight into the terminal's native scrollback using `renderMessage`, so wheel-scroll, click-drag selection, and copy are all native terminal behavior everywhere; there is no mouse capture, no DECSET modes, and no in-app scroll/search/copy-mode keys. `View()` renders only a small bounded live region (`liveRegionView`): the optimistic pending-user line, in-flight deltas/thinking, and the working spinner (which appends the in-flight tool detail + elapsed from `console_chat.tool_started`/`tool_finished`, cleared on finish/idle/error — `bgtasks.go`), wrapped to content width and tail-clipped to min(chrome-measured budget, `liveRegionCap`=12 rows) — the cap keeps headroom above the frame so a `tea.Println` insert (which scrolls against the frame still on screen; the shrunken repaint only flushes on the next frame tick) can't push live rows into native scrollback permanently. For the same reason `printNewMessages` splits each rendered message into `maxPrintRows` chunks (terminal height minus live-cap+chrome allowance, floor 1) and the status bar truncates to one physical row. `View()` clamps the chrome block (`clampChrome`, view.go) and the joined frame to never exceed `m.height` — dropping optional sections then tail-truncating — so a long turn or a tiny terminal can never push the composer off the bottom, then pads the frame to the terminal bottom with `lipgloss.PlaceVertical(target, lipgloss.Bottom, frame)`, where `target := max(frameHeight, m.height-m.printedLines)`. `printedLines` counts physical scrollback rows at the *full terminal width* (`physicalRows`, print.go, mirroring bubbletea v2's `cursedRenderer.insertAbove`: one row per line plus one per full multiple of width a line's display width consumes) rather than `lipgloss.Height` at content width, since `tea.Println` scrolls at full width; a bounded tail buffer of recently-printed messages (`printedTail`, capped to ~one screenful of `maxHeightSeen`, the largest terminal height observed so far rather than the current height) lets resize re-render and re-count at the new dimensions instead of drifting — bounding eviction to the current height alone would over-evict on a shrink and undercount permanently after a later grow. Live deltas and thinking are cleared on `console_chat.turn` state=idle (mirroring the backend's `clearLive()` at turn completion), so a finalized reply lives only once, in scrollback. Print-once/dedupe is an absolute-count high-water mark: `printedTotal` tracks how many of the server's DB-absolute `MessagePage.Total` rows have been printed; `newMessagesToPrint` (print.go) diffs a reloaded page against it so WS reconnects and `messages.updated` reloads print only genuinely new rows and never rewrite already-printed scrollback — a stale/gapped `printedTotal` degrades to reprinting the whole fetched window rather than fabricating a gap. The first tail page is loaded in `Run()` and printed on the first `WindowSizeMsg` (real width isn't known at `Init` time); `Run()` also clears the terminal (screen + scrollback, cursor home) once before starting the program so the inline transcript begins at a clean top.

# console Package

Server-owned tool catalogue + dispatcher for `kind='console'` `agent_sessions` (see [api/CLAUDE.md](../api/CLAUDE.md#console-sessions)), served over `GET`/`POST /api/v1/console/tools*`.

## Profile Invariant

The console `apirun.ToolEnv` has no `WorkflowInstanceID` — a console session isn't bound to a run — so the base registry (`registry.go`) includes **only session-independent tools**: an explicit allowlist of `tools_builtin.Builtins()` entries (`reusedBuiltins()`) plus console-only handlers (`tools_workflow*.go`, `tools_project.go`, `tools_ticket.go`, `tools_artifact.go`, `tools_dynamic.go`, `tools_plan.go`, `tools_consult.go`) that take an explicit `instance_id`/`ticket_id`/project-guard instead of reading state off the env. Every session-bound lifecycle/findings/artifact-write tool (`agent_*`, `findings_*`, `emit_findings`, `workflow_skip`, `chain_next_*`, `run_subworkflow`, `read_document`, `artifact_add`) is excluded — `BuildRegistry` errors if an allowlisted name goes missing from `Builtins()` (rename guard), never silently drops it. `BuildRegistry(d, catalogue)`'s second arg further filters to a `console.Profile`'s allowlist when non-empty (nil/empty = every tool above, today's pre-profile behavior) — see Console-Chat Profiles below.

Because those ids are caller-supplied, **every** tool taking an `instance_id` is project-guarded: console handlers via `loadGuardedInstance` (`helpers.go`), and the reused `workflow_continue`/`workflow_fail` builtins via the orchestrator's `APIWorkflowControl` adapter (see [orchestrator/CLAUDE.md](../orchestrator/CLAUDE.md#misc)). A console token must never act on another project's instance. The `ticket_list`/`ticket_get`/`ticket_current` readers (`tools_ticket.go`, the picker feeding `workflow_run`'s `ticket_id`) take no project arg at all — they scope to `env.ProjectID` via `TicketRepo`/`TicketSvc`, so there is no cross-project id to guard.

`delegate`/`get_delegation` (`tools_delegate.go`) are the one exception to "session-bound tools are excluded": unlike `consult`, they are intentionally exposed to console (T0) sessions, routing through `Deps.Delegator` (`orchestrator.APIDelegator`) instead of `env.Delegator` — the implementation creates its own hidden host workflow instance since a console session has no `WorkflowInstanceID` to spawn workers under.

## Current Ticket

`ticket_current` returns the ticket the session is working on, read from `agent_sessions.ticket_id` for `env.SessionID` (full ticket when set, `{"current_ticket":null}` otherwise — never an error). `agent mcp-external` stamps that column from its git branch when it opens a standalone console tool session; console-chat sessions are project-scoped but have no implicit ticket.

Console-initiated workflow runs (`dynamic_workflow`, `workflow_run`) start via `Deps.Orch.StartConsoleWorkflow`, attributing the instance's `origin`/`origin_session_id` to `"console"` + the launching `env.SessionID`.

## ArtifactSvc Nil in ToolEnv

`env.go`'s `NewToolEnv` leaves `ToolEnv.ArtifactSvc` nil: `artifacts.workflow_instance_id` is `NOT NULL REFERENCES workflow_instances(id)` with `foreign_keys(1)` on, and a console session owns no instance, so any write through the shared `web_fetch`/etc. artifact path would FK-fail after already writing the blob. `web_fetch` takes its documented nil-artifact-store branch instead. The console `artifact_list`/`artifact_get` tools (`tools_artifact.go`) hold their **own** `*service.ArtifactService` from `Deps` and take an explicit `instance_id`, so they are unaffected.

## workflow_wait

`workflow_wait` (`tools_workflow_wait.go`) long-polls a guarded instance's v4 state, blocking until a transition-relevant digest differs from `since_digest` or timing out with `changed=false`. Digest contents, `buildTrackingState` projection, `WaitBroker` wiring, terminal-response extras: [REFERENCE.md](REFERENCE.md#workflow_wait) — read before changing the digest or wake path.

## Dispatch

`Dispatch(ctx, reg, env, name, args)` (`dispatch.go`) is the one call site `api.handleCallConsoleTool` uses; `ErrToolNotFound` maps to the endpoint's 404. `Specs(reg)` backs the catalogue endpoint, sorted by name.

## Console chat sessions

`ChatService` (`chat_service.go` + `chat_session.go`/`chat_spec.go`/`chat_sink.go`/`chat_events.go`) owns `kind='console_chat'` `agent_sessions` lifecycle: it mints the row + bearer token, builds a `spawner.EngineSpec`, starts a `spawner.ConsoleEngine` (via an injectable factory defaulting to `spawner.GetConsoleEngine`), tracks the turn state machine (a message landing mid-turn queues and auto-delivers as the next turn — [REFERENCE.md](REFERENCE.md#askuserquestion-question-cards--mid-turn-prompt-queue)), and pumps `EngineEvent`s onto the session's WS channel (`hub.BroadcastSession`, see [ws/CLAUDE.md](../ws/CLAUDE.md)). Tools reach the server the same way a human console session's do: the engine's `--mcp-config`/profile already points at `agent mcp-external`, which adopts this pre-minted session from `NRFLO_CONSOLE_TOKEN`/`NRFLO_CONSOLE_SESSION_ID` and proxies to the same `console.BuildRegistry`+`NewToolEnv` tool routes (`requireConsoleSession` accepts both `console` and `console_chat` kinds). Engines hold no `processInfo`, so stall/nudge/restart are structurally unreachable — this is not a kind check anywhere in the spawner/orchestrator. `ChatService.InvokeTool` (`chat_service_invoke.go`) runs one tool deterministically against the chat's own profile catalogue via the same `BuildRegistry`+`Dispatch` path, outside any model turn (`guardIdle` 409s while a turn is running, without starting one); it persists a `user_input`+`tool` `agent_messages` pair and broadcasts `messages.updated` on the session channel. With `inform_model`, a compact result digest is appended (not replacing) to the session's pending `seedContext`, folded into the caller's next `SendMessage` turn only.

`nrflo_server console` is a thin native client in `internal/consoleui`: the server-owned catalog builds claude/codex/api engine options from one enabled-model list, exposing a model once per supported mode with that mode's effort list and the row's default effort. Chat create (REST body / socket param `reasoning_effort`) accepts an override validated against the selected mode before it reaches `EngineSpec.ReasoningEffort`; trusted socket methods return a scoped bearer locally, remote clients use a service token, detach leaves the engine live, and explicit close tears it down. `AttachPTY` (`chat_pty.go`) exposes a claude chat's raw terminal to the web PTY relay as a pure viewer (`spawner.ConsolePTYTarget` — the engine keeps sole PTY-read ownership and viewer disconnect never touches it).

The third engine, `api`, has no CLI/PTY: `ChatDeps.Tools` injects the console tool profile (`BuildRegistry`/`Specs`/`NewToolEnv`) into `spawner.EngineDeps.API` unconditionally in `Create`, so claude/codex simply ignore it. Both resolvers use `ModelService.Get`: CLI validates provider↔engine and reads CLI fields (unknown IDs pass through raw), while API rejects unknown/disabled rows or an empty `api_model`. When `api_native_tools_enabled` is on (default off) and the chat has a workdir, the api engine additionally offers approval-gated, workdir-jailed native file/bash tools; off, it has no local tools and registers no approvals.

An engine that dies is not a stuck chat: `pumpChatEvents` ends the turn on every `EventError` (each one is turn-terminal), and when `Events()` closes — Stop, or the engine dying on its own — it tears the session down (drop from the map, `CloseConsoleChat`, killing the bearer token) and pushes `console_chat.turn` state=idle **last**, so a subscriber that sees it knows the row is already closed. Without that, an engine that died mid-turn would pin the turn `running` and 409 every later message forever. Both close paths (`Close`, `engineExited`, in `chat_service_close.go`) also call `spawner.DropProactiveRestartState`, releasing the session's `globalRestartStore` entry so it doesn't leak past the chat's lifetime.

## Console-Chat Profiles

`profiles.go`'s built-in registry (`ProfileByName`/`ListProfiles`) bundles a named chat configuration (`Catalogue`, `NativeToolPolicy`, default model/effort, `ContextBudgetTokens`, `RefineryDefault`, `SystemTemplateID`, `SiblingFlows`) threaded into the started `EngineSpec` and persisted on `agent_sessions.console_profile`, re-applied identically on rotation. Full profile roster and threading/rotation/persistence mechanics: [REFERENCE.md](REFERENCE.md#console-chat-profiles).

## Project Skills

`skills.go`'s `discoverSkills` scans `<project root_path>/.claude/skills/*/SKILL.md` per request (no watcher), parsing frontmatter `name`/`description` with a dir-name fallback; `ListSkills` backs `GET /api/v1/console/skills`. `SendMessage` (`chat_service_turn.go`) matches a leading `/name` in the raw text against the project's skills and, when matched, hands the engine a `spawner.UserTurn{Text, *SkillMatch}` instead of applying the seed-context prepend — unmatched/unknown `/text` is sent verbatim. Pass-through-vs-expand for a matched skill is entirely each `spawner.ConsoleEngine`'s own decision (Rule 6), never a name check here.

## Sibling Chats

`ChatService.SwitchModel`/`OpenHandsSibling` (`chat_service_sibling.go`), gated on `Profile.SiblingFlows`, open a new sibling chat (a different engine/model, or the `t0-hands` profile) instead of ever mutating the origin's live engine, seeded with the origin's latest refinery digest as first-message context (`chatSession.seedContext`, consumed once by the sibling's first `SendUserTurn`). Both broadcast `console_chat.sibling_opened` (`{origin_session_id, sibling_session_id, reason}`) on the origin's session channel.

The engine name a chat row was started with is persisted in `agent_sessions.console_engine`, so `GET /api/v1/console/chats` does not depend on the in-memory session map. `pumpChatEvents` is the single writer of the `console_chat.approval_resolved`/`console_chat.thinking` session pushes for both engines — an engine's `RequestApproval`/`ReplyApproval`/resolved-notification paths only emit `spawner.EventApprovalResolved`, exactly once per registered id (whoever *drops* the pending entry owns the emit, so a reply racing a timeout cannot double-resolve) and never push WS/audit themselves. The REST reply route accepts `allow`/`allow_for_session`/`deny`/`answer` (AskUserQuestion cards — see REFERENCE.md above); the pump normalizes the spawner's resolved decisions to `allow`/`deny`/`answer` on the WS push (codex maps `allow_for_session` natively, the claude/api engines keep a server-side per-tool-name allowlist). That allowlist is visible in the detail snapshot (`session_approvals`) and pushed as the full list on `console_chat.session_approvals` whenever it changes; `DELETE .../session-approvals/{tool}` revokes one entry (codex cannot list or revoke — its session scope lives in the app-server); token usage is pushed there too, but a claude chat's also fans out from `socket/handler_context.go`, so that one event legitimately arrives twice (idempotent).

`ChatService.SetYolo` mirrors `RevokeSessionApproval`: it toggles the engine (claude/api mutate a mutex-guarded flag, effective on the next tool call; codex updates in-memory state only, effective on the next rotation), write-throughs `agent_sessions.console_yolo` (NULL inherits the global default, resolved by `resolveSessionYolo` on rotation so an override survives it), then pushes the full boolean on `console_chat.yolo`. `POST`/`DELETE /api/v1/console/chats/{sid}/yolo` turn it on/off.

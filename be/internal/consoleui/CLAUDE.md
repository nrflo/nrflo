# consoleui Package

Native Bubble Tea v2 client for server-owned `console_chat` engines; the server-driven resume/profile/brand/model/mode/effort picker lives in `select*.go`, and the live chat reconciles transcript, approvals, turn state, delegation state, and reconnects in `model.go`/`update*.go`. Enter submits or queues, approval/question handling is interactive, Ctrl+C interrupts, Ctrl+D detaches, Ctrl+X closes, Ctrl+Y toggles yolo, and Ctrl+T opens the flow overlay (`graph.go`/`view_graph.go`). Composer history is project-scoped when possible (`input_history.go`), while `/` and `/invoke ` completion retain Up/Down selection behavior.

Layout: transcript fills the top of the screen; the activity line (`working…`, `delegating…`, notices, and history position) sits directly above the single-line auto-growing composer (`DynamicHeight`, 1-8 rows), and the bottom status bar carries engine/model, profile, project, connection, context, cost, background count, permissions, git state, and cwd. While a `/` or `/invoke ` query matches, the status row becomes a one-line completion strip showing as many option names as fit plus `N/total`; Up/Down changes selection, Enter completes it, and Esc dismisses it, without changing frame height. Background counts come from `GET /api/v1/workflows/active` on WS connection and lifecycle events (`bgtasks.go`, never polling).

`/invoke ` switches the same completion status to the chat's `GET .../tools` catalogue; selecting a tool runs a sequential composer-based arg prompt (per `input_schema` field, each prompt labelled with its type e.g. `queries (array, required):`) then a one-line `[i]`-inform-toggle confirm that dispatches `POST .../invoke` (transcript rows arrive over WS, no local echo). The pure state machine and schema parsing live in `invoke.go`; `array`-typed fields coerce plain-text/scalar input into a one-element JSON array (JSON arrays pass through unchanged), and confirming with invalid JSON in an `object`-typed field routes back to that field instead of dispatching.

`renderMessage` (view_message.go) prefixes every printed row's first line with the message's persisted `created_at` as muted local `HH:MM:SS` (continuation lines indented `timePrefixWidth`; dropped when the timestamp is absent/unparseable or the terminal is too narrow). Every transcript category renders through ONE pipeline: `preRender` reduces content where raw text isn't human prose (`system_notice` → skipped; `task_notification`/`system_turn` collapse via `view_notice.go`; tool-family rows collapse to ONE clipped line — `tool · [Name]` head plus the payload's first line, ellipsis-marked when more followed or the row overflowed width (`headLine`/`clipOneLine`; no wrap, so one logical row is always one physical row); everything else passes through TrimSpace'd), then `fitWidth` expands tabs, ANSI word-wraps to width and clips overflow (`view_wrap.go`), then `styleFor` colors by role alone. Printed lines must never contain tabs or exceed the terminal width — `ansi.StringWidth` counts `\t` as zero while terminals advance to the next tab stop, so either desyncs bubbletea's `insertAbove` row math and corrupts the screen. Role is conveyed by color alone — no `you`/`assistant` header rows: user input light blue (117), assistant near-white (254) vs dim-gray (244) tool/thinking rows.

The main model renders inline (`view.AltScreen = false`, `select.go`'s short-lived resume/new-session picker stays alt-screen). Completed transcript rows are never held in model state or a viewport — they are emitted once via `tea.Println` (print.go) straight into the terminal's native scrollback using `renderMessage`, so wheel-scroll, click-drag selection, and copy are all native terminal behavior everywhere; there is no mouse capture, no DECSET modes, and no in-app scroll/search/copy-mode keys. `View()` renders only the frame — a small bounded live region (`liveRegionView`: optimistic pending-user line and in-flight deltas/thinking) above the chrome, clamped to `m.height` (`clampChrome` drops optional sections then tail-truncates). The animated working indicator, with the in-flight bracketed tool name + elapsed from `console_chat.tool_started`/`tool_finished` (cleared on finish/idle/error — `bgtasks.go`), lives in the footer only. Bottom-anchoring comes from the renderer: bubbletea v2's inline region anchors at the cursor, so `clearScreenSeq` (written once by `Run()`) erases screen+scrollback then parks the cursor on the terminal's bottom row, and every `insertAbove` re-anchors the frame there. Two renderer constraints shape printing (all learned the hard way — verify against `cursedRenderer.insertAbove` before changing): (1) inserts land only in the free rows above the on-screen frame, so `printNewMessages` splits each message into `maxPrintRows` chunks (height minus `liveRegionCap`=12 + chrome allowance, floor 1) and returns them as one `tea.Sequence` (`tea.Batch` would land chunks out of order); an empty body is an insert no-op, so empty-rendered messages are skipped and a blank line alone in a chunk prints as `" "`. (2) A frame SHRINK is top-anchored (chrome floats up, blanks below), so the WHOLE frame's height ratchets via `m.frameBand`: any shrink — live region clearing at idle, the composer losing a row, an approval box closing — is padded back with top rows each carrying a single space (a fully empty row is skipped by the renderer's diff, which then never blanks vacated rows and corrupts the screen), and only `printNewMessages` releases band rows (≤ the rows it prints, prefixed by a 50ms `printReleasePause` so the shrunken frame flushes before the inserts refill exactly the vacated rows). Live deltas and thinking are cleared on `console_chat.turn` state=idle (mirroring the backend's `clearLive()`), so a finalized reply lives only once, in scrollback. Print-once/dedupe is an absolute-count high-water mark: `printedTotal` tracks how many of the server's DB-absolute `MessagePage.Total` rows have been printed; `newMessagesToPrint` (print.go) diffs a reloaded page against it so WS reconnects and `messages.updated` reloads print only genuinely new rows and never rewrite already-printed scrollback — a stale/gapped `printedTotal` degrades to reprinting the whole fetched window rather than fabricating a gap. The first tail page is loaded in `Run()` and printed on the first `WindowSizeMsg` (real width isn't known at `Init` time).

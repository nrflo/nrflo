# Spawner Reference

Deep mechanics for this package. The auto-loaded map lives in [CLAUDE.md](CLAUDE.md).

### CLI tool registry attach

`read_document` swaps per `SupportsNativeDocRead()`: Claude → path variant; codex → `ReadDocumentHybridHandler` (path + image media → MCP image blocks, vision on codex ≥0.51; PDFs rasterized to page PNGs via host `pdftoppm`, path-only fallback). Transport per adapter — Claude: `--mcp-config`/`--strict-mcp-config`/`--allowedTools mcp__nrflo__*` (`configureClaudeMCPTools`) plus `--disallowedTools` denying native delegation (`cli_adapter_claude.go`); codex: an `[mcp_servers.nrflo]` table in `CODEX_HOME/config.toml` with embedded bridge env (`appendCodexMCPServer`, codex doesn't forward parent env).

### api-via-cli hybrid

When `Config.APIViaCLI==true` and the model provider is `anthropic`, `prepareAPIViaCLISpawn` (`spawner_prepare_apicli.go`) turns the api spawn into a `cli_interactive` Claude session while deliberately retaining the row's `APIModel`, `APIContext`, and `APIEfforts`. Because the CLI picks its context window from the `--model` string (not `proc.maxContext`), the `APIModel` gets a `[1m]` suffix when `APIContext` is 1M and exceeds `CLIContext`, so the real window matches the reported one. Tool registry, API system prompt, PTY delivery, and MCP bridge behavior stay api-mode-shaped. OpenAI models stay on the in-process runner.

### Codex app-server backend

`codexAppServerBackend` (`codex_appserver_backend.go`) drives `codex app-server` over newline-delimited JSON-RPC stdio (`codex_appserver_client.go`), spawned with `-c agents.enabled=false` blocking native delegation (`appServerArgs()`/`codex_delegation.go`) — the autonomous path routes here because app-server is the richer structured channel (thread/tokenUsage->context_left, typed rate limits, thread/resume), not because PTY hooks are unavailable; see "### Codex PTY hook sidecar" below for the validated 0.145 PTY-hook behaviour. Events map to the standard `Sink` via `dispatchAppServerEvent` (`codex_appserver_events.go`): agentMessage→text, command/webSearch→tool, mcpToolCall→invoke+result, `thread/tokenUsage`→`context_left`, turn lifecycle→heartbeat, typed rate-limit. Completion stays socket/DB-driven; idle/nudge re-issues a `turn/start` with the `finish-reminder`. `CodexAdapter` is still used for model mapping + `ClassifyExit`; its PTY methods back the take-control resume launch below. `appServerArgs()` also passes `-c project_doc_fallback_filenames=["AGENTS.md","CLAUDE.md"]` (`codex_project_doc.go`) so a project whose repo has no `AGENTS.md` still gets its root `CLAUDE.md` loaded as the codex project doc (first existing name wins per directory, so nrflo's own `AGENTS.md`->`CLAUDE.md` symlink loads once, not twice — and for this repo the flag is a no-op). This is a CLI override rather than a config.toml key because a key appended after a table header is silently absorbed by that table, and a duplicate root key is a hard parse error against the user's own `~/.codex/config.toml`.

**`thread/tokenUsage/updated` payload (validated against codex-cli 0.145.0).** `TokenUsageBreakdown` carries `totalTokens`/`inputTokens`/`cachedInputTokens`/`outputTokens`/`reasoningOutputTokens` (required) plus `cacheWriteInputTokens` (optional, default 0); `ThreadTokenUsage` wraps `{last, total, modelContextWindow}`, both full breakdowns. `last` fires once per upstream Responses-API call (not per turn) and is byte-identical to the internal `rawResponse/completed.usage`; `total` is the thread-cumulative sum. `codexUsageBreakdown`/`codexTokenUsage` (`codex_appserver_events_usage.go`) mirror this schema; `dispatchTokenUsage` reconciles the ledger against `last.inputTokens` (exact) instead of back-deriving from `ContextLeftPct`, and bills `total`'s fresh (non-cached, non-cache-write) input plus cache-write tokens through `SetSessionCostUsage`. Raw app-server events (`rawResponse/completed`, `rawResponseItem/completed`) exist in the binary's method table but are undocumented/internal-only, need both `initialize.capabilities.experimentalApi` and an undocumented `thread/start experimentalRawEvents` param to unlock, and — confirmed live — add zero accounting value over `tokenUsage.last` while `rawResponseItem/completed` alone pushes megabytes of full prompt/response text per turn through `notifyCh`. Decision: `threadStartParams` (`codex_appserver_backend.go`) does not set `experimentalRawEvents`.

**Nested package `CLAUDE.md` files do NOT reach codex workers.** Codex's project-doc chain only walks *ancestors* of cwd, and every nrflo spawn sets cwd = `Config.ProjectRoot` (`cmd.Dir = workDir`), so the chain is always exactly one directory: the repo root. `be/internal/*/CLAUDE.md` and friends are invisible to a spawned codex agent — it must read them with its own tools (the root doc is the map and points at them). Codex also does not expand `@`-imports in project docs. Closing that gap needs a different mechanism (e.g. injecting the doc tree into the prompt the spawner builds), not this flag; `codex_project_doc_cli_test.go` pins both the positive and the negative.

**Thread resume (`SupportsResume()`/`SupportsTakeControl()` both true).** `codex_appserver_resume.go` implements `thread/resume` — validated against the installed codex-cli 0.145.0 (`app-server generate-json-schema`): required `threadId`, no `effort` param (effort still rides only `turn/start`, same as `thread/start`). The thread's rollout JSONL lives under the per-session `CODEX_HOME/sessions/...` and is written starting from the first `turn/start` — a thread that never completed a turn has no rollout, and resuming it fails with rpc `-32600 "no rollout found for thread id ..."`; `startOrResumeThread` treats any `thread/resume` rpc error (this one included) as non-fatal and falls through to `thread/start` + the full rendered prompt, so a resume failure can never turn a recoverable restart into a hard spawn failure.

**Handoff ownership.** `Start` arms `proc.resumeHandoff = &codexThreadHandoff{threadID, profileDir}` right after every thread id is known (fresh or resumed), before the event loop — ownership of the temp `CODEX_HOME` profile dir moves from `run`'s own defer to the handoff at that point (`run`'s defer only removes the dir when `resumeHandoff` is still nil). `defer close(proc.doneCh)` is registered first in `run` so it runs last, after the handoff is armed and the profile-dir defer decision is made; `monitorAll` only reads `proc.resumeHandoff` after `<-proc.doneCh`, so no lock is needed. From there the handoff either transfers to a successor proc (`transferResume`, only when the old proc set `resumeOnRelaunch`) or is discarded (`discardResume`, removing the dir) at every other terminal path: `finalizePhase`, `cancelRunningProcs`, and `relaunchWithBookkeeping` for any relaunch that didn't transfer it.

**fail_restart-only policy.** Only the auto-restart-failed-agent branch in `spawner_monitor.go` sets `proc.resumeOnRelaunch = true` (alongside `failRestartCount++`). Every other relaunch reason stays fresh-spawn by design: low-context and proactive-rotation shed context on purpose (the refinery digest / `to_resume` finding already carry forward); stall restarts resuming a wedged conversation would reproduce the wedge; tier fallback (`relaunchForFallback`) deliberately changes model/provider/mode and the thread is bound to the original; rate-limit restarts stay fresh for now (a one-line policy change at that single site if wanted later). Console chat rotation is unrelated — a console codex chat mints a fresh thread per `Start` regardless; adding `EngineSpec.ResumeThreadID` would be a separate feature.

**Resuming a profile: config.toml rewrite.** `resolveCodexProfileDir` reuses the handoff's dir on a resume (instead of `MkdirTemp`) and re-runs `writeCodexSessionProfile` on it, which truncates and rewrites `config.toml`'s `[mcp_servers.nrflo]` table with `nrfloBridgeEnv(proc.sessionID, ...)` for the NEW session id — the `sessions/` rollout tree itself is untouched, so the resumed thread's history is intact while the MCP bridge points at the live session.

**Cost baseline.** Codex's `thread/tokenUsage` reports thread-CUMULATIVE totals, so a resumed thread's first usage event would re-bill the dead session's pre-crash tokens onto the new `agent_sessions` row. `transferResume` snapshots the dying session's cumulative usage (`SessionCost`) into the handoff via the optional `costBaselineCapture` sub-interface right before the handoff moves; `startOrResumeThread` then calls `SetSessionCostBaseline(proc.sessionID, ...)` on the resume path, and `costStore.setUsage` subtracts that baseline (clamped at 0) from every subsequent cumulative report.

**Take-control hand-off.** `TakeControlExtras()` implements the optional `interactiveHandoff` sub-interface, returning `InteractiveExtras{CodexHome: b.profileDir}` while the backend is alive (including immediately after `Kill`, since `profileDir` is never cleared by `Kill`). `registerTakeControlResumeLaunch` asserts the interface (no name-check on the backend) and forwards `CodexHome` into the PTY resume launch, so `codex resume <thread_id>` runs against the live per-session `CODEX_HOME` instead of the viewer's real `~/.codex`, where the thread's rollout would not exist.

**Codex-side compaction.** codex 0.145 can compact a thread's own history mid-session even though nrflo's kill→save→relaunch already owns context shedding: it emits a typed `item/started`+`item/completed` with `item.type=="contextCompaction"` (no token fields), followed by an extra `thread/tokenUsage/updated` checkpoint whose `last` is the post-compaction footprint with `inputTokens==0` and every other `last.*`/all of `total.*` unchanged from the prior event — `dispatchTokenUsage` (`codex_appserver_events_usage.go`) treats `last.inputTokens<=0` as "not a usage sample" (bumps the heartbeat, returns) rather than falling back to `total.inputTokens`, since that fallback used to feed the thread-CUMULATIVE input total into `ComputeContextLeftPct`, spuriously tripping the low-context kill→save→relaunch once cumulative input crossed the restart threshold. `appServerArgs()` also pins `-c model_auto_compact_token_limit=1000000000` (`codex_appserver_compaction.go`) so nrflo's own threshold stays the single authority in the common case; the pin beats both the model preset (every 0.145 preset ships `null`) and the user's `~/.codex/config.toml` (copied verbatim into the per-session profile by `writeCodexProfileForSession`), validated live via `-c` override precedence. codex's per-thread token/rollout budgets (`TokenBudgetConfigToml`/`RolloutBudgetConfigToml`) are server-pushed, not client-settable (`-c token_budget=...`/`-c rollout_budget=...` fail `--strict-config` as unknown fields) — so remote compaction stays possible and is *detected*, not disabled. On the completed `contextCompaction` item, `dispatchContextCompaction` resets `context_left` to 100 both in the DB (`sink.UpdateContextLeft`) and, via the returned `appServerSignal.compacted` flag, on `proc.contextLeft` in the run loop — `readContextLeftFromDB` is deliberately monotone-decreasing, so the DB write alone would leave the stale pre-compaction watermark and `monitorAll` would still fire the kill. The same event resets the context ledger (`ledger.resetForCompaction`, wired via `EventContextCompacted` in `codexLedgerEmitter`): pre-compaction blocks are gone from the model's context, so `reconcileUsage` would otherwise rescale them into a fictional composition; every entry is marked `Superseded` (history preserved for the UI) and a one-token `LedgerKindInjected` placeholder is appended so the next real `tokenUsage` event has a non-zero estimate to scale against.

**Known gap (unchanged by this feature).** `POST /{tickets,projects}/{id}/workflow/resume-session` (`handlers_resume_launch.go`) still passes `ResumeSessionID: session.ID` (the nrflo session id, not the codex thread id), and by the time that endpoint runs the profile dir has already been swept — fixing it needs the thread id persisted on `agent_sessions` (no such column today).

### Console Engine

`ConsoleEngine` (`console_engine.go`) is the conversation counterpart to `ExecutionBackend`; `GetConsoleEngine` is the one provider-name switch for Codex, Claude, and direct API engines. It takes a `Sink` + `EngineSpec` — no `*Spawner` or `*processInfo` — which makes autonomous nudge, stall, and restart policies structurally unreachable.

**Normalized event set.** `EngineEvent.Type` is one of `text_delta`, `text`, `thinking`, `tool_invoke`, `tool_result`, `approval_request`, `turn_started`, `turn_completed`, `token_usage`, `error`. These are provider-agnostic; `codexEngine` produces them via `dispatchAppServerEvent`'s `emit EventEmitter` parameter (`codex_appserver_events.go` / `codex_appserver_events_engine.go`), the same mapper the autonomous `codexAppServerBackend` uses.

**Nil-emitter contract.** `dispatchAppServerEvent` and its helpers (`dispatchCompletedItem`, `emitMcpToolCall`, `dispatchTokenUsage`) take `emit EventEmitter`; every emit call goes through `EventEmitter.emit`, which is a no-op when the emitter is nil. `codexAppServerBackend` always passes `nil`, so the autonomous spawn path's `Sink` calls, control-signal (`appServerSignal`) derivation, and heartbeat bumps are byte-for-byte unchanged — the only new work on that path is a nil check per event. Deltas (`item/agentMessage/delta`, `item/reasoning/textDelta`, `item/reasoning/summaryTextDelta`) are live-only: they bump the heartbeat and emit an `EngineEvent` but never call `RecordHookMessage` — the canonical text/thinking is persisted once, on `item/completed`.

**Completed-item field shapes.** `item/completed` carries a *ThreadItem*, and `appServerItem.Content`/`.Summary` are `json.RawMessage` because the same field NAME holds different shapes per item type: a `reasoning` item's `content`/`summary` are arrays of plain strings (`ReasoningThreadItem`, both protocol generations — the `{type,text}`-block shape belongs to the raw `ReasoningItem`, which `item/completed` never carries), while a `userMessage`'s `content` is an array of input blocks. Typing either strictly makes `json.Unmarshal` fail for the other type, and `dispatchCompletedItem`'s error guard then silently drops the whole item — so decoding stays per-type (`reasoningText`), not on the shared struct.

**Events channel + Stop.** `Events()` is a 256-buffered channel and `codexEngine.emit` selects on a `stopping` channel that `Stop` closes *before* it waits on `loopDone`. Without that, a consumer in the natural `for ev := range eng.Events() { … eng.Stop() }` shape — which stops draining the instant it calls `Stop` — parks `runLoop` in a blocking send on a full buffer, so it never re-enters its select to observe `ctx.Done` and `Stop` hangs forever. `runLoop` also clears `turnActive` on exit, so a connection dropped mid-turn cannot pin the engine into permanently rejecting `SendUserTurn` with `ErrTurnActive`.

**Turn interruption.** Codex retains the id returned by `turn/start` and sends `turn/interrupt` with both thread and turn ids; Claude writes Ctrl+C to its PTY and lets the Stop hook own the idle transition; API mode cancels only the current `Conversation.SendTurn` context. All three return `ErrNoActiveTurn` while idle and preserve their session-level context for the next message.

**Console-chat yolo.** `ConsoleEngine` (`console_engine.go`) is the provider-agnostic conversation driver used by console chats; `InterruptTurn` cancels only the active turn and preserves the engine's conversation. Engine death remains observable through `Events()`, so `console.ChatService` cannot leave a dead turn pinned; engines hold no `processInfo`, making nudge/stall/restart policies structurally unreachable. Codex uses app-server, Claude uses the PTY + hooks path, and `apiConsoleEngine` uses an in-process `apirun.Conversation`. `EngineSpec.NativeToolsCSV`/`Sandbox`/`NativeToolPolicy`/`ContextBudgetTokens` carry a `console.Profile`'s native-tool/budget policy into each engine and the rotation threshold — profile owns these values; see [console/CLAUDE.md](../console/CLAUDE.md#console-chat-profiles). `EngineSpec.Yolo` (default-ON `console_yolo` setting) auto-approves tool calls on all three engines while still emitting `EventToolInvoke`. `ConsoleEngine.SetYolo`/`Yolo` mutate a mutex-guarded flag alongside each engine's approval state: claude/api take effect immediately (read by the same short-circuit `EngineSpec.Yolo` feeds), codex persists the change but only applies it on the next `thread/start` (rotation) since app-server has no live approval-policy mutation.

**One approval protocol generation** (validated against `codex app-server generate-json-schema`, codex-cli 0.145.0; see `console_engine_codex_approval.go`'s `approvalDecisionWire`): `item/commandExecution/requestApproval` and `item/fileChange/requestApproval` both resolve `ApprovalApprove`/`ApprovalApproveForSession`/`ApprovalDeny`/`ApprovalAbort` to `accept`/`acceptForSession`/`decline`/`cancel`.

`decline` means the command is not executed but the turn continues; `cancel` also interrupts the turn. `serverRequest/resolved` is a *notification* (no id) meaning the server resolved a pending request elsewhere (or it timed out) — `codexEngine.runLoop` intercepts it ahead of `dispatchAppServerEvent` and drops the matching pending entry without replying. `ReplyApproval` drops a pending entry only *after* the reply is written: `ApprovalDecision` is a bare string, so an unmappable value (or a transport failure) must leave the id retryable rather than consuming it and leaving codex blocked on that JSON-RPC id forever.

**Why `item/permissions/requestApproval` is not decision-shaped.** Its response shape is `{permissions, scope, strictAutoReview}`, not `{decision: ...}` — it configures a permission grant, it doesn't approve/deny one action. `codexEngine.onServerRequest` does not special-case it; like every other unhandled server request (`item/tool/requestUserInput`, `mcpServer/elicitation/request`, `item/tool/call`, `account/chatgptAuthTokens/refresh`, `attestation/generate`, ...) it falls through to `client.replyError`, so codex is never left blocked on a request the engine does not implement. Both the console engine and the autonomous `codex_appserver_backend.go` now share this table — the backend via `autoApproveWire`, replying `replyError` on any miss instead of guessing.

**Delegation blocking.** `appServerArgs()` (`codex_delegation.go`) passes `-c agents.enabled=false` for `codexEngine`: an app-server-spawned child is invisible to nrflo, so native delegation must stay disabled for server-owned console conversations. The prior mechanism, repeatable `--disable multi_agent --disable multi_agent_v2 --disable enable_fanout` flags, was a proven silent no-op against codex-cli 0.145.0: the live tool registry was unchanged (spawn_agent/followup_task/send_message/wait_agent/interrupt_agent/list_agents all still present) and `codex debug prompt-input` was byte-identical with and without the flags — `enable_fanout` had already reached stage=removed. `agents.enabled=false` removes all six collaboration tools with no collateral damage, and `-c` deep-merges over a user's own `[agents]` table (their other fields, e.g. `max_depth`, survive; only `enabled` is forced off) rather than clobbering it. The thread/turn-level `MultiAgentMode` option was considered and rejected: `ThreadStartParams`/`ThreadResumeParams`/`TurnStartParams` reference no delegation field at 0.145.0, and its only variants (`explicitRequestOnly`/`proactive`/`{custom}`) have no `disabled` case, so it cannot block delegation even if it were wired.

**Config.toml-shrink negatives (item 1 watch-items, validated against codex-cli 0.145.0).** The trust entry stays in config.toml rather than becoming a `-c` override: codex's dotted-path `-c` splitter does not unquote a path segment, so `-c 'projects."/p".trust_level="trusted"'` creates a literal `"\"/p\""` key while the real `/p` entry keeps its old value (seen via `config/read`); the inline-table form does merge correctly but would require threading the per-session workDir into `appServerArgs()` (today pure/no-arg) and into `BuildInteractiveCommand`/`PrepareUserSession` as well, with symlink resolution duplicated at each site, for no net code reduction — the file is written anyway for auth.json. `[mcp_servers.nrflo]` stays in the file because moving it to argv would expose `NRF_SESSION_ID`/`NRF_WORKFLOW_INSTANCE_ID`/`NRFLO_PROJECT`/`NRFLO_SOCKET` — and the console engine's `NRFLO_CONSOLE_TOKEN` bearer — in the process table, readable by any local user via `ps`. Ticket watch-item #33184 (an MCP tool-cache opt-out key) is not actionable at 0.145.0: `mcp_servers.*` accepts exactly `command`/`args`/`env`/`environment_id`/`enabled`/`tool_timeout_sec` (+ HTTP-only `url`/`bearer_token_env_var`/`oauth_*`), and `--strict-config` rejects `cache_tools`/`tool_cache_enabled`/`cache_tool_list`/`enable_tool_cache`/`disable_tool_cache` — none of the 96 `ConfigToml` root keys is MCP-cache-related.

**Rotation digest seeding.** `EngineSpec.SeededContext` is the rotation digest-seeding seam: `console.rotate()` sets it unconditionally (no engine-name branch); the api/codex engines consume it once into their first post-rotation request (`console_engine_api_seed.go`/`console_engine_codex_seed.go`), while `claudeEngine` never reads the field since its `UserPromptSubmit` hook already re-injects the digest — consuming it there too would double-inject.

**apiConsoleEngine system prompt.** `apiConsoleEngine.Start` renders its system prompt from the `api-console-system-prompt` injectable — a distinct id from the worker's `api-system-prompt`, left unseeded so a fresh DB falls back to the `consoleAPISystem`/`consoleAPIFSSystem` constants.

**Yolo mode.** `EngineSpec.Yolo`, resolved once per chat create/rotate from the default-ON `console_yolo` global setting (`val != "false"`), short-circuits `claudeEngine.RequestApproval`/`apiConsoleEngine.requestToolApproval` to an immediate allow (after the `allowedForSession` check, before any pending-approval registration) and makes `console_engine_codex.go`'s `Start` set `ApprovalPolicy="never"` instead of the `"on-request"` default; `EventToolInvoke` is still emitted so tools remain visible in the transcript, and a `NativeToolPolicy=none` profile's read-only sandbox is unaffected since yolo governs approval, not tool surface.

**System-prompt resolution + delivery.** An agent def's or chat profile's `system_template_id` resolves ahead of both the global `claude_system_prompt_override_enabled` gate and the mode default (`resolveSystemPromptOverride`/`EngineSpec.SystemPrompt`). Delivery stays per-channel — claude via `--system-prompt-file`, api via its conversation `System` — except codex, which has no system-prompt flag anywhere (autonomous or console) and instead gets the rendered text prepended to the first turn's prompt body, so its byte cap is the initial-turn/prompt-file limit, not a dedicated one.

### claudeEngine (console_engine_claude*.go)

`claudeEngine` drives a console conversation over the same PTY + Claude-hooks transport the autonomous `cli_interactive` backend uses — no headless `-p`/stream-json. `Start` writes per-session MCP and hook settings, creates a PTY keyed by `spec.SessionID`, and registers with `ConsoleHub`; PTY output is dropped because heartbeat, transcript text, approvals, and turn boundaries come from hooks. Its argv carries none of the managed-session bypass/deny-list/safety-hook flags.

**Raw-terminal viewer + prompt-echo dedupe.** `claudeEngine` implements `ConsolePTYTarget` (`console_engine_claude_viewer.go`): the ferry stays the PTY's only reader (two concurrent `ptmx.Read`s steal bytes) and forwards output copies to at most one attached viewer; input/resize go through `ViewerWrite`/`ViewerResize`. Human-typed prompts from an attached terminal persist via the UserPromptSubmit hook: `NotifyUserPrompt` claims only the engine's own `SendUserTurn` echo (exact text, matched once — `pendingEcho`), so the socket handler records everything else.

**Hook wiring via ConsoleHub, not a direct channel.** Unlike `codexEngine` (JSON-RPC request/response over its own client), `claudeEngine` never talks to the CLI process directly for events — Claude's `--settings` hooks call `nrflo_server agent record-event --console`, which reaches the socket server, which calls into `spawner.ConsoleHub` (`console_hub.go`), which looks up the engine by session id and invokes one of four `consoleTarget` methods: `NotifySessionReady` (SessionStart → unblocks `SendUserTurn`'s TUI-ready wait), `NotifyTurnEnd` (Stop → flush transcript, clear `turnActive`, emit `EventTurnCompleted`, call `Sink.OnTurnComplete`), `NotifyContextLeft` (statusline via `agent.context_update` → `EventTokenUsage`), and `RequestApproval` (PreToolUse → the blocking approval path below). `ConsoleHub.Register`/`Unregister` run from `Start`/`Stop`; every hub method returns `handled=false` for a session with no registered engine, so autonomous sessions are unaffected.

**Timeout ladder (strictly increasing).** Server-side `RequestApproval` wait `consoleApprovalTimeout`=600s < the CLI's `agent record-event --console` select deadline `consoleHookDeadline`=630s (`cli/agent_hooks.go`) < its socket read deadline `consoleHookReadDeadline`=660s ≈ the settings PreToolUse hook's own `timeout`=660s (`BuildConsoleSettingsJSON`). The read deadline is the rung that is easy to miss: `Client.Execute`'s default is a hard 5 minutes — *below* the 600s approval wait — so the console path must call `ExecuteAndUnmarshalWithReadDeadline`. On the default, a human answering after 300s would have the socket read time out and deny the tool while the engine still recorded their "allow", silently diverging the decision from what claude did.

Every layer denies rather than erroring non-zero: a hook that exits non-zero or prints nothing leaves claude falling back to its own interactive permission prompt, which nobody can answer in a server-driven PTY. So a `--console` PreToolUse call always exits 0 and prints a deny `hookSpecificOutput` on *every* no-decision path — select deadline, transport error, and server-not-running/no-session (which return before the socket call at all, and so must deny explicitly instead of exiting silently the way an autonomous hook does).

**Turn delivery.** `SendUserTurn` mirrors `deliverPrompt`'s PTY discipline (`backend_interactive_helpers.go`): wait for SessionStart (`claudeSessionStartTimeout`=20s), persist the `user_input` row *before* writing so transcript-tailed assistant rows cannot land first, write the body, wait `claudeSubmitDelay`=150ms, then write the submit `\r`. Both waits matter — coalescing body+CR into one PTY read lets the TUI swallow the submit, leaving a turn typed but never sent (and `turnActive` stuck, since only the Stop hook clears it). `claudeBootstrapFloor`=1.5s applies only to the FIRST turn: it exists to let the TUI finish its initial paint, so charging it to every later turn is pure latency. All four durations are injectable engine fields, zeroed in tests (Rule 4).

**permissionDecision wire vocabulary.** `claudeDecisionWire` (`console_engine_claude_approval.go`) maps `ApprovalApprove`/`ApprovalApproveForSession`→`"allow"`, `ApprovalDeny`/`ApprovalAbort`→`"deny"` (abort carries reason `"aborted by user"`). Claude has no native PreToolUse equivalent of codex's `acceptForSession`, so `ApprovalApproveForSession` is remembered engine-side: `ReplyApproval` records the pending approval's tool name in a session allowlist and `RequestApproval` auto-allows that tool (by name — coarser than codex) without emitting an approval request. An unmappable decision still errors and leaves the pending id retryable, matching `codexEngine.ReplyApproval`'s drop-after-write rule. `decision` is deprecated for PreToolUse per the installed CLI's own docs; only `permissionDecision` is used there (Stop/PostToolUse/UserPromptSubmit keep the old `decision:block` shape untouched, see `cli/agent_hooks.go`'s `renderHookDecision`).

**Transcript tail offsets.** `flushTranscript` reconstructs the transcript path via the proc-free `claudeTranscriptPath(env, workDir, sessionID)` (`inband_rate_limit.go`, shared with `lastAssistantText`; it symlink-resolves workDir first — claude encodes its *resolved* cwd, so `/var/...` workdirs would otherwise never match on macOS) and tails it with the same byte-offset + only-complete-lines pattern as `socket/transcript_thinking.go`: a partial trailing line is left unconsumed, and `offset > size` restarts at 0 (rotated/truncated file). It runs on both a `tailLoop` ticker and hook-triggered flushes (`RequestApproval`, `NotifyTurnEnd`) so text surfaces promptly around tool calls and turn ends — which means concurrent flushes from three goroutines, so a dedicated `flushMu` serializes the whole read-process-advance sequence: two overlapping flushes would otherwise both start from the same offset and emit + persist every new line twice. Assistant `text` blocks emit `EventText` and persist via `emitAgentText` (category `"text"`); `thinking` blocks emit `EventThinking` only — no Sink row, so socket's `tailThinking` (triggered by the *same* Claude hooks on the *autonomous* path) stays the single writer of `"thinking"` rows and neither path double-inserts for a console session (`tailThinking` only ever fires from a `PreToolUse`/`PreCompact` hook call that reaches `handleAgentRecordEvent`, which console sessions also send, but the row category split means both can coexist without collision). `tool_use`/`tool_result` blocks are intentionally skipped — those already surface as `EventToolInvoke`/hook-driven events, not transcript rows.

## Interactive CLI Backend

`cliInteractiveBackend` (`backend_interactive.go`) spawns CLI agents in a PTY. Per-adapter divergence lives entirely in the adapter file — `backend_interactive.go` has no name-checks. Key `CLIAdapter` methods for interactive use (see `cli_adapter.go`):

- `BuildInteractiveCommand(opts)` — PTY-friendly command without batch flags. When `opts.ResumeSessionID` is set, appends `--resume <id>` (Claude) or the equivalent resume argument (Codex).
- `PrepareInteractive(opts)` — returns `InteractiveExtras` (Codex: per-session CODEX_HOME profile dir).
- `DeliversPromptInline()` — true for Codex (argv positional); false for Claude (PTY stdin write after readiness delay).
- `NeedsTerminalQueryReplies()` — true for Codex (TUI sends terminal capability probes during init).
- `BumpsOnPTYBytes()` — opt-in heartbeat via PTY bytes. Claude returns false (hooks drive the heartbeat). Codex keeps returning true even though PTY user sessions now emit hooks too (see sidecar paragraph below) — the managed `cli_interactive` spawn is still routed to the app-server backend, so this only affects human-session PTY paths and stays the documented fallback floor.

`writeCodexProfileForSession` (`cli_adapter_codex_profile.go`) writes the per-session `CODEX_HOME` (auth + a workdir `trust_level="trusted"` entry, without which codex 0.145 blocks on a trust dialog); called by the app-server backend's `Start`.

### Prompt delivery is confirmed, not assumed

`deliverPrompt` (`backend_interactive_helpers.go`) can only *infer* TUI readiness — `waitForReady` takes SessionStart (authoritative, `sessionStartTimeout`=10s) else a first-byte fallback, then gates on PTY quiescence + `bootstrapFloor`. Both inferences fail under a wide layer fan-out, because a quiet PTY during a **starved** bootstrap is byte-for-byte indistinguishable from a quiet PTY parked on a ready input loop. The paste + CR then lands mid-bootstrap, the TUI redraws over it, and the prompt is gone with no error anywhere: the process is healthy, `context_left` stays 100, zero `agent_messages` are recorded, and the only recovery is `checkStall`'s start-stall two minutes later. Measured at ~21% of nodes across two 7-wide fan-outs (both variants observed: SessionStart arriving at ~4s and blowing a then-3s timeout, and the primary path with entirely normal 750–900ms quiescence).

So `submitPromptWithRetry` (`prompt_delivery_retry.go`) confirms the write instead. `proc.hasReceivedMessage` is the acknowledgement — for adapters where `BumpsOnPTYBytes()` is false it flips only on a real recorded event, and the `UserPromptSubmit` echo (seq 0) is always the first — so a re-submit fires only when literally nothing was recorded, i.e. when the turn provably never began. That is what makes re-sending safe: it cannot duplicate a prompt the CLI already took. Up to `maxPromptSubmits`=3 attempts, `promptAckTimeout`=12s each (an order of magnitude above the ~1s a healthy spawn takes); a write error is terminal rather than retried, an exited process counts as acked, and exhausting the budget falls through to stall detection unchanged. Adapters that bump on PTY bytes get one write and no ack wait — paint traffic alone would satisfy the signal.

### Settings Merge (Claude interactive)

`BuildInteractiveSettingsJSON` (`hooks_settings.go`) returns `--settings` JSON with `hooks` (PreToolUse/PostToolUse → `nrflo agent record-event`) and `statusLine`. `mergeInteractiveSettings` deep-merges safety JSON + hooks JSON, concatenating hook arrays on key conflict so `statusLine` survives.

### Codex PTY hook sidecar

`hooks_settings_codex.go`'s `buildCodexHooksJSON`/`writeCodexHooksForSession` write a Claude-shaped `CODEX_HOME/hooks.json` — `{"hooks":{"SessionStart":[{"matcher":"*","hooks":[{"type":"command","command":"<nrflo> agent record-event"}]}], …}}` — for exactly five validated events (SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, Stop), into the per-session profile dir both `PrepareUserSession` (`user_session_codex.go`) and `PrepareInteractive` (`cli_adapter_codex.go`) already create; a write failure only logs a warning (PTY bytes remain the liveness floor). `--dangerously-bypass-hook-trust` is mandatory — validated against codex-cli 0.145.0: without it hooks are silently skipped (no warning, no error) — and is emitted in `PrepareUserSession` unconditionally (nrflo always owns that CODEX_HOME) but in `BuildInteractiveCommand` only when `opts.CodexHome != ""`, so a resume launch with no CodexHome (`registerTakeControlResumeLaunch`, `registerResumeLaunch`) never bypasses hook trust on the user's real `~/.codex`. Codex 0.145 hook payloads are byte-compatible with Claude's (`hook_event_name` CamelCase, `session_id`/`cwd`/`model`/`transcript_path`) and the hook subprocess inherits the full parent env (including `NRF_SESSION_ID` from `buildPtyEnv`), so the existing `agent record-event` CLI + `handleAgentRecordEvent` socket handler need no changes. `writeCodexProfileForSession` (shared with the app-server backend and console engine) never writes hooks.json, so those profiles stay hook-free.

## Context Save

The kill-time (`initiateContextSave`, `context_save.go`) and proactive (`initiateContextSaveProactive`, `context_save_proactive.go`) save paths both route through `contextSaveViaAgent`, so a single change covers both. `contextSaveViaAgent` decides whether an agent save is needed at all: stepwise defs skip it (the cursor is the save), and so does a fresh autonomous refinery slot digest — `freshDigestAfterForcedFold` calls `RefinerySidecar.FoldNow` and then re-checks `freshSlotDigest` (`digest_freshness.go`). Forcing the fold is what makes that decision deterministic: autonomous folds are debounced ≥30s, so a session burning from `refinery_fold_start_context_pct` to the relaunch threshold inside one debounce window would otherwise reach this point with no digest, spawn a saver, and only then have its scheduled fold land — becoming the handoff the relaunch actually reads while the saver's output is discarded. A nil sidecar, a shut gate or a failing fold model all leave the answer unchanged, so the agent path below stays the fallback rather than becoming a dependency. Only when no digest covers the session does it reach `spawnContextSaver` (`context_save_agent.go`). `spawnContextSaver` loads the `context-saver`/`context-saver-api` system agent def via `GetForBackend` (selected by the dying agent's backend, keeping the saver mode-compatible by construction) for prompt/tools/execution_mode/timeout, but no longer runs it on that def's fixed model: `contextSaverModel(proc, sysDef.Model)` sources `Model`/`ReasoningEffort` from the dying agent's own resolved spawn state on `processInfo` — `proc.modelID` (parsed via `parseModelID` to strip the `cli:` prefix) and `proc.resolvedEffort` — rather than re-deriving from the static `s.config.Agents[proc.agentType]` map, so LowConsumptionMode's model override (`spawner.go`) and `resolveReasoningEffort`'s per-project/workflow `agentDef.ReasoningEffort` DB override are both reflected, matching what the dying agent actually ran with. `proc.resolvedEffort` is set at each of the three `resolveReasoningEffort` call sites (cli, api, api-via-cli) in `spawner_prepare*.go`. Falls back to `sysDef.Model` (effort `nil`) when `proc.modelID`'s bare model is empty, so the saver's own def stays the safety net. Mirrors the inline api compaction at `apirun/conversation_compact.go:118`, which sets `Model`/`ReasoningEffort` from the running agent's own `Config`. A nil effort override means the ephemeral saver spawn resolves the inherited model's `DefaultEffort`, which now matches the dying agent's own default since it runs the same model.

## Proactive Restart

`context_restart.go` holds a process-global, session-keyed `restartStore` (mirrors `ledgerStore`) tracking per-session `restartsDone`/`lastRestartAt`/`lastBoundaryTurn`. `resolveProactiveRestartThreshold` mirrors `resolveContextBudget`: a non-nil `agent_definitions.proactive_restart_threshold_tokens` wins (0 = disabled), NULL falls through to the `proactive_restart_threshold_default` config key (default 250000). Config knobs (`contextConfigInt`, code-side defaults, no seed migration): `proactive_restart_min_interval_sec` (600), `proactive_restart_max_per_session` (0 = unlimited but logged), `proactive_restart_boundary_window_turns` (10), `proactive_restart_console_pct` (75 = fire when the console window is 75%+ used). `ProactiveRestartCoordinator` (a `ws.Listener`, registered pre-Run in `api/server.go` next to `refinery.Manager`) stamps a session's current ledger turn as its `lastBoundaryTurn` whenever a `findings.updated` broadcast (the only watched event type, since it's the only one that carries `Event.SessionID` — `service.BroadcastFromCtx` stamps it from `BroadcastCtx.SessionID`) fires for that session.

`shouldRotate` (`context_restart_policy.go`) is the pure decision: over threshold, idle, boundary recent enough, min-interval elapsed, under the per-session cap, and the run's last plan item (`lastPlanItemInFlight`, `context_save_proactive.go` — the highest-layer materialized `workflow_instance_nodes` row with a still-open `agent_sessions` row) not in flight. `spawner.ProactiveRestartDecision` wraps it against the global store for both call sites.

**Autonomous path.** `checkProactiveRestart` (`context_save_proactive.go`) runs from `monitorAll`'s still-running branch right after `checkIdleNudge`, reusing the exact idle-window computation (`idleWindowElapsed`) the nudge loop uses as its own mid-tool-chain guard — any recent activity resets `lastMessageTime`, so an elapsed idle window is "safe to interrupt" by the same logic a nudge already relies on. On fire it sets `proc.lowContextSaving`/swaps `doneCh` exactly like the manual-restart branch, then runs `initiateContextSaveProactive`: kill→flush→save via the context-saver agent, same as `initiateContextSave` (no console/refinery digest exists for an autonomous session, so it always saves via the context-saver agent), setting `proc.proactiveRotationPending`. `relaunchForContinuation` (`completion.go`) checks that flag to reset `restartCount` to 0 and bump `proactiveRestartCount` instead of the normal increment, logging tokens-before (captured at trigger time) / tokens-after (the new session's ledger total) together.

**Console path.** `console.ChatService.maybeRotate` (`chat_service_rotate.go`) runs from `pumpChatEvents` on every `EventTurnCompleted` (the idle boundary is the call site itself — no ledger-turn concept for claude/codex console engines). It requires a non-empty refinery digest (`repo.RefineryDigestRepo`, keyed to the console `agent_sessions.id`, survives rotation) and a token estimate derived from the session's last `EventTokenUsage.ContextLeftPct` against `EngineSpec.MaxContext` (`chatSession.currentTokens`, tracked via `chatSession.noteContextLeft`) crossing `ProactiveRestartConsoleThreshold` — `proactive_restart_console_pct` of the window, since that window-bounded estimate can never reach the autonomous ledger-sized default. `rotate` stops the old engine, builds a fresh `EngineSpec` with a new `CLISessionID` (`EngineSpec.effectiveCLISessionID()` — claude's `--session-id` arg and transcript path use it; `SessionID` stays the stable identity for hub/MCPEnv/WS so hooks keep resolving), starts a new engine of the same kind, swaps it onto `chatSession.engine` (mutex-guarded via `getEngine`/`setEngine` — HTTP-handler goroutines read it concurrently with the pump goroutine's swap), resets the session's context tracking to 100% left, and emits `ws.EventConsoleContextRotated`. `pumpChatEvents` tracks a local `rotated` bool set by `maybeRotate`'s return value so its normal channel-close teardown (which would otherwise close the chat row) is skipped for the old engine — `rotate` already launched a fresh `pumpChatEvents` goroutine bound to the new engine's `Events()` channel before returning. Codex needs no `CLISessionID` split: `thread/start` mints a fresh thread on every `Start`.

## Rate-Limit Restart

`cli_interactive`: a non-zero exit matching a rate-limit pattern (adapter `ClassifyExit`) triggers `handleRateLimitRetry` (`rate_limit_restart.go`) — broadcasts `agent.rate_limited`, registers `result=continue/reason=rate_limit`, persists `rate_limit_until_ts`, sets `finalStatus=CONTINUE`. `waitForRateLimitRetry` sleeps exponential backoff (`min(InitialBackoff·2^(n-1), MaxWait)`), or waits for a known subscription reset via `resetAwareDelay` (`rate_limit_config.go`, +30s, ≤8h). `rateLimitRetryCount` is separate from `failRestartCount` and carries across relaunches.

In-band: a 529 the Claude CLI prints as text without exiting is caught on idle by `handleInBandRateLimit` (`inband_rate_limit.go`) — same retry, relaunch uses `--fallback-model`.

`api` agents: `apirun.classifyProviderError` returns `RetryClassRateLimit`; `apiBackend.Start` runs the same dance. `rateLimitConfig` loads for both lanes in `prepareSpawn`.

Config keys (project > global, via `pool.GetProjectConfig`/`GetConfig`): `rate_limit_enabled` (default `true`), `rate_limit_initial_backoff_sec` (`60`), `rate_limit_max_wait_sec` (`3600`), `<adapter>_limit_patterns`/`<adapter>_error_patterns` (extra comma-separated patterns).

## Idle/Nudge Loop

Active for `cli_interactive` backends only (`proc.nudgeMax > 0`). Idle window: `idleStartTimeout` (default 2 min, no output yet) or `idleAfterMessageTimeout` (default 4 min, after first output). On idle: write `finish-reminder` to PTY stdin, broadcast `agent.nudged`, persist `nudge_count`. After `nudgeMax` nudges and another full idle window: `AgentSvcReal.Fail(reason="unresponsive_after_nudges")` + `RequestTerminalSignal(sessionID, "fail")`. Configurable via `Config.Idle*Sec`/`NudgeMax`.

End-of-turn completion is *also* enforced in-band by the Claude **Stop hook** (registered in `hooks_settings.go`; decided in `socket/handler_record_event.go` `handleStopHook`): when an autonomous turn ends without a completion tool, the server returns a `decision:block` carrying a finish-reminder (up to `stopBlockCap`=3 blocks), then fails the session.

**Notification-triggered immediate nudge.** `socket/handler_record_event_notification.go`'s `handleNotification` classifies each Claude `Notification` hook payload via `classifyNotification` — a structured field first (`type`/`notification_type`), else a substring match on `message` ("waiting for your input"→idle; "needs your permission"/"permission to use <tool>"→permission, tool captured when present); anything else is `unknown` and recorded exactly as before this feature existed, with no downstream call. For `idle`/`permission`, after recording the row it calls `h.signaler.TriggerIdleNudge(sessionID, kind)` (nil-safe, best-effort). `Orchestrator.TriggerIdleNudge` resolves session→`o.runs[wfiID]`→`rs.spawners[sessionID]` exactly like `BumpLastMessage` (returning nil on any miss — this is what excludes console/observer sessions, which have no run/spawner entry); on a hit it calls `Spawner.TriggerIdleNudge`, a non-blocking send onto `nudgeRequestCh` (buffered 16, mirrors `bumpMessageCh`). `monitorAll`'s top-of-loop select drains `nudgeRequestCh` and calls `triggerImmediateNudge`, which re-guards `proc.backend.Name()=="cli_interactive"` and `proc.nudgeMax>0` (excluding codex app-server and the nudge-less api-via-cli lane — defense in depth alongside the orchestrator's run/spawner-miss guard) before picking the same `sendNudge`-vs-`handleNudgeAutoFail` branch `checkIdleNudge` uses; it does **not** call `handleInBandRateLimit` or any wall-clock check, which stay exclusively in `checkIdleNudge`. **No-double-nudge invariant:** `recordNudgeSent` resets `proc.lastMessageTime` on every nudge (in-band or wall-clock), so the immediate nudge defers the wall-clock `checkIdleNudge` path by a full idle window — the two paths cannot both fire for the same idle episode.

## Stall Detection

Checked per-poll in `monitorAll`; skipped when `stallRestartCount >= maxStallRestarts` (15).

- `stall_start_timeout_sec` (agent_definitions) — seconds with no output before a start-stall; NULL = global default (120s), 0 = disabled.
- `stall_running_timeout_sec` (agent_definitions) — seconds with no output after first message; NULL = global default (480s), 0 = disabled.
- `Config.GlobalStallStartTimeout`/`GlobalStallRunningTimeout` — override hardcoded defaults when agent def has NULL. Priority: per-agent def > global config > hardcoded.

On stall: broadcast `agent.stall_restart`, SIGTERM→SIGKILL, flush messages, `result=continue`, 15s delay, relaunch.

## Tier Fallback

`tier_fallback.go` implements the advance engine. `chainEntryModelID(entry)` derives `cliForProvider(provider)+":"+modelID`; `isProviderBuildError(err)` classifies a build-time provider-construct failure via the `errProviderBuild` sentinel (`wrapProviderBuildErr` wraps `api_mode_disabled`, `BuildAPIProvider` errors, and unsupported api/cli mode-for-model in `spawner_prepare.go`/`spawner_prepare_api.go`) — a structural error (template load, node not found, unknown CLI adapter) is NOT wrapped and never advances. `spawnEntryWithBuildFallback(ctx, req, modelID, phase, wfiID, chain, startPos)` loops chain entries from `startPos`, retrying only on `isProviderBuildError`, and is called from `Spawn()` at `startPos=0`; an empty chain (main workflow-phase agents) falls back to a bare `spawnSingle(modelID)` call, byte-identical to pre-tier-fallback behavior.

`shouldAdvanceChain(proc)` is the monotonic guard: `ok` only when `proc.hardProviderFail` is set AND `proc.chainPos < len(proc.chain)-1`. HARD-vs-soft reuses each backend's existing RetryClass verbatim — `apirun.classifyProviderError`'s `RetryClassError` calls `proc.SetProviderHardFail()` in `runner_loop.go` (api mode); CLI/codex's `CLIAdapter.ClassifyExit`→`RetryClassError` sets `proc.hardProviderFail` directly in `completion.go`'s `handleCompletion`. `RetryClassRateLimit` never sets the flag on any path, so 429/529 always stays in-band.

`monitorAll`'s FAIL branch calls `tryChainFallback` (guarded on `proc.hardProviderFail`) BEFORE the `maxFailRestarts` branch: on advance it best-effort saves via `saveForFallback` (`contextSaveViaAgent`, no kill step — the process is already dead), marks the session `continue`/`provider_fallback`, and relaunches via `relaunchForFallback` through the shared `relaunchWithBookkeeping` closure (same terminal-signal/ledger/refinery-sidecar/session-cost bookkeeping `relaunchAndRegister` uses for ordinary continuations). `relaunchForFallback` sets `req.ExecutionModeOverride`/`ReasoningEffortOverride` from the next entry (cross-mode allowed — `prepareSpawn` honors both, winning over agentDef/config), copies continuation fields the same way `relaunchForContinuation` does, sets `newProc.chain`/`chainPos`, and resets `hardProviderFail=false`. `relaunchForContinuation` (same-model relaunches: low-context/stall/failRestart) also copies `chain`/`chainPos` and resets `hardProviderFail=false`, so a same-model retry can never re-trigger an advance from a stale flag. Chain exhaustion (`ok=false`) leaves the session `FAIL`; only a chain that actually advanced (`chainPos>0`) and hit its last entry (`chainExhausted`) re-registers with `chain_exhausted` — a proc that never advanced (no chain, or a length-1 chain still at `chainPos==0`) keeps the reason its completion path classified. broadcast: `agent.provider_fallback` (`session_id`, `new_session_id`, `agent_type`, `from_provider`, `to_provider`, `from_mode`, `to_mode`, `chain_pos`).

## Context Ledger

`contextledger` (`ledger*.go`) is a process-global, session-keyed in-memory ledger of ordered context blocks (dialog/tool_use/tool_result/file_read/image/injected), written EXACT from apirun's `Config.Observer` in api mode, EXACT-ish by tail-parsing the Claude transcript from the `monitorAll` tick in cli mode, and EXACT from codex app-server events — `codexLedgerEmitter`'s `EventTokenUsage` case reconciles against `EngineEvent.Usage.InputTokens`, the exact per-response `tokenUsage.last.inputTokens` codex publishes, rather than back-deriving from the integer `ContextLeftPct` (which quantized to 1% = 2,584 tokens on a 258,400 window). Token estimates are still a bytes/4 heuristic per block; reconciliation scales them to match provider-reported usage. Same-sha/path re-entry marks the prior entry superseded, and a debounced `agent.context_ledger` WS event carries totals-by-kind — `GET /api/v1/sessions/{id}/context-ledger` snapshots it, and the ledger drops when the session ends.

## Context Watcher

`context_watcher*.go`: an api-mode policy engine over the context ledger. Default budget derives per-model: `context_budget_fraction` (0.65) × max-context. `agent_definitions.context_budget_tokens` (NULL → config `context_budget_default`, 0 = disabled) triggers selective GC over budget, evicting superseded → stale tool_results/file_reads (unreferenced ≥ `context_decay_turns`, default 20) → completed dialog, keeping the pinned prefix + recent window verbatim; idle gaps ≥ `cache_ttl_sec` (default 300) bypass the `min_epoch_interval_calls` (default 20) throttle for a free deferred rewrite. Wired via the nil-safe `apirun.Config.Watcher` seam (mirrors `Observer`); CLI/codex restart policy is out of scope here. Its `ContextCostEstimator` (`context_watcher_cost.go`, `pricingCostEstimator`) resolves the session's model row pricing once (cached for the watcher's lifetime) and estimates a GC's saved cost as evicted tokens re-billed at the cache-read rate — the rate retained context would cost on every future turn if not evicted; NULL pricing or an unknown model yields 0.

Duplicate eviction is not a separate policy: the ledger marks the older duplicate `Superseded` at append (`dedupKeyFor` — path identity for file_read, content-SHA for dialog/tool_use/tool_result; `ledger.go:42-81`), and `selectEviction` evicts superseded entries (tier 0) before decay and dialog (`context_watcher_policy.go:37-38`). Because superseded entries are excluded from `epochSummary.TotalTokens` (`ledger.go:195`) — the value the over-budget trigger reads (`context_watcher.go:151`) — duplicates exert 0 residual token pressure, and `reconcileUsage` (`ledger.go:151-172`) redistributes real provider tokens onto survivors so the trigger keeps tracking true usage. The watcher runs api-mode only (`backend.go:163`, `console_engine_api.go:163`), both fed by `observeAPIBlock` which SHA-dedups every kind, so no watcher path lacks duplicate detection.

## Session Cost

`sessioncost.go` mirrors `ledger_store.go`'s process-global, session-keyed shape: a `costEntry` per session holds cumulative input/output/cache-read/cache-write token counters plus a running USD cost, computed from the `models` row's per-MTok `price_*` columns (`model.PriceClass()`'s underlying pricing, resolved once at `register`; NULL pricing leaves the entry `PricingKnown=false` and cost 0). Feeds: api turns call `addUsage` (delta); claude CLI (both workflow `ledger_cli.go` and console `console_engine_claude_transcript.go` tailers) parses `message.usage` off each transcript line via the shared `ingestClaudeTranscriptUsage` helper (`claude_transcript_usage.go`) and bills through `AddSessionCostUsageOnce`, deduped per session by transcript-entry `uuid`/`message.id` so an offset-reset re-read never double-bills; codex app-server's cumulative `thread/tokenUsage/updated` calls `setUsage` (overwrite) — codex now feeds `total.cacheWriteInputTokens` through `setUsage`'s 4th arg (previously hard-coded 0), with `fresh = inputTokens - cachedInputTokens - cacheWriteInputTokens` billed at the full input rate (`freshInputTokens`, `codex_appserver_events_usage.go`). A 1s debounce gate (mirrors `ledgerBroadcastDebounce`) coalesces bursts into one `repo.AgentSessionRepo.UpdateCost` (targeted UPDATE of `agent_sessions.tokens_json`/`cost_estimate`, no per-call write) plus one broadcast — project-scoped `session.cost_updated` for autonomous spawns (`Spawner.broadcastSessionCost`), session-channel for console chats (registered in `console.ChatService.create`). `RegisterSessionCost`/`FinalizeSessionCost` (flush+drop) are the exported lifecycle entry points; `SessionCost(id)` is the read-side snapshot the console/statusline/consoleui surfaces call.

## Session Timing

`sessiontiming.go` mirrors `sessioncost.go`'s process-global, session-keyed shape for wall time instead of tokens: a `timingEntry` accumulates four cumulative bucket-seconds (thinking, tool-arg streaming, text, tool wait) from inter-event deltas, keyed off the previous timestamped event to the next one (API latency rides with the following block). Only `cli_interactive` sessions are registered (`RegisterSessionTiming` in `spawner_util.go`, gated on `executionMode == "cli_interactive"`) — `api`-mode sessions have no per-block timing source yet, so registering them would force-flush an all-zero, non-NULL `time_buckets_json` at finalize instead of the NULL the FE contract expects. `ledger_cli_timing.go`'s `classifyTranscriptEntry` maps a Claude transcript entry's type (assistant `tool_use`/`thinking`/`text` blocks, user `tool_result`) to a bucket with `tool_use > thinking > text` precedence; `recordTranscriptTiming` wires it into `RecordSessionTimingEvent`, deduped per transcript-entry `uuid` like `AddSessionCostUsageOnce`. Codex's app-server feed (`ledger_codex.go`) has no per-item timestamps, only turn-level `startedAt`/`completedAt`, so it feeds `RecordSessionTimingEvent` with wall-clock dispatch time (empty dedup key) — a coarser model-time-vs-tool-wait split, not exact per-block timing. A 1s debounce flush mirrors `sessioncost.go`'s, persisting via `repo.AgentSessionRepo.UpdateTimeBuckets` (targeted UPDATE, no broadcast). `RegisterSessionTiming`/`FinalizeSessionTiming` (flush+drop) are the exported lifecycle entry points, called at the same sites as their cost counterparts.

### Autonomous Refinery Sidecar

`Config.RefinerySidecar` (declared as the narrow `spawner.RefinerySidecar{StartSession,StopSession}` interface, satisfied by `*refinery.Manager`) rides the same lifecycle sites as running-cost tracking, one call each: `startBackend` (`spawner_util.go`) calls `StartSession(sessionID, projectID, workflowInstanceID, nodeID)` right after `markAgentStarted`, gated on `cfg.RefinerySidecar != nil && prep.executionMode == "cli_interactive"` — the autonomous session shape (script agents report no usage, api-mode already gets console-style folding elsewhere). `StopSession(sessionID)` fires immediately *before* each `FinalizeSessionCost` call — `cancelRunningProcs` (kill), `relaunchAndRegister` (continuation/stall/timeout relaunch), and `finalizePhase` (normal completion) — so a session's final fold still attributes usage to a running-cost row that hasn't been dropped yet. Only the main-workflow `orchestrator_loop.go` `baseCfg` sets `RefinerySidecar = o.RefineryMgr`; system one-off spawns (context-saver, consult, planner, observer) build their own `spawner.Config` and simply omit the field, so they get no sidecar — no name-checks, by construction. Because `relaunchForContinuation` preserves `workflowInstanceID`/`nodeID` across a kill->relaunch chain, the digest slot `StartSession`/`StopSession` key on is identical before and after relaunch, so the new session's first fold reads the prior session's last fold as its previous digest.

## Stepwise Prompt Assembly

A `prompt_mode='stepwise'` agent def (`service.PromptModeStepwise`, `agent_definitions.steps` a `[]model.StepDefinition` JSON array) renders differently at every prompt-assembly seam upstream of `startBackend`, so cli_interactive, the codex app-server backend, and api all get it automatically. `isStepwiseDef`/`stepwiseDefFor` (`template_stepwise.go`) are the ONE gate (Rule 6) — never `def.PromptMode == "stepwise"` at a call site.

**Block order.** `loadTemplate` (`template.go`) resolves the agent def once near the top (threaded into both `resolveSystemPromptOverride` and the stepwise appender) and, at the very end — after `expandProjectFindings`, immediately before return — calls `s.appendStepwiseBlock`. For full mode / a nil def this is a no-op (`template` returned unchanged, byte-identical to the pre-stepwise render). For a stepwise def it appends: the rendered `stepwise-guidance` injectable (readonly, `${STEP_INDEX}`/`${STEP_TOTAL}`/`${STEP_TITLE}`/`${STEP_ID}`/`${STEP_REVISION}` vars) + a titles-only `## Steps (step N of M)` outline marked completed/current/locked + a `### Current step` header (step_id + revision) + that step's full `Instruction`. A future step's Instruction is never rendered.

**Cursor-vs-def-steps precedence.** `resolveStepwiseState` reads `stepengine.Engine.State(wfiID, nodeID)` first — the cursor snapshot is authoritative and immutable, so a mid-run def edit never reaches an in-flight run. It falls back to `json.Unmarshal(*def.Steps)` (index 0, nothing completed, revision 1) only when there is no cursor: Preview (`nodeID==""`), interactive L0 starts, or a pool-less spawner.

**Snapshot-before-loadTemplate ordering.** `prepareSpawn` (`spawner_prepare.go`) calls `s.snapshotStepCursor` right after the agent def load and before `s.loadTemplate`, so the cursor row exists before the agent's first tool call. `snapshotStepCursor` wraps `stepengine.Engine.Snapshot` with nil-pool/mode guards and best-effort error logging (`template_stepwise.go`) — an unsnapshottable cursor degrades to the def-steps fallback render above, never fails the spawn. `Snapshot` is idempotent (`ON CONFLICT DO NOTHING`), so a relaunch's repeat call never resets in-progress `revision`/`current_index`/`completed`.

**The previous_data stepwise branch.** `fetchPreviousDataAndReason` (`template_findings_prev.go`) gates on `stepwiseDefFor` right after the continued-session row is read: when the def is stepwise, it calls `s.stepwiseResumeData` (`template_stepwise_resume.go`) and — when that renders non-empty (>=1 completed step) — returns it directly, never reading the `to_resume` finding. `stepwiseResumeData` builds `## Completed Steps (verified)` from `stepengine.Engine.CompletedEvidence` (one block per completed step: snapshot-declared `required_findings` keys — never the agent-supplied `CompletedStep.EvidenceKeys` — their stored values, and the resolved/unresolved path split via `handoff.ResolvePathCandidates`), then appends `handoff.NarrativeSection(digest)` when a fresh refinery slot digest exists, capped via `foldfmt.CapBytes`. It deliberately does not call `handoff.Compose` — no generic Verified State, no transcript tail. A stepwise def with zero completed steps still returns `stepwiseResumeData`'s (empty) render unconditionally once `stepwiseDefFor` matches — `fetchPreviousDataAndReason` never falls through to the digest/`to_resume`/`composeOrNarrative` path for a stepwise def, completed steps or not.

**The context-saver skip.** `contextSaveViaAgent` (`context_save.go`) checks `stepwiseDefFor` before the existing `freshSlotDigest` branch: a stepwise def logs and returns without the `context_saving` broadcast or a `spawnContextSaver` call — the cursor IS the save, since every accepted step's evidence already lives in findings + the cursor's `completed` JSON.

### complete_step + rotation

`complete_step` (`apirun/tools_builtin/complete_step.go`) is the ONLY caller of `stepengine.Advance`, exposed exclusively to stepwise defs: `buildAPIRegistry` (`spawner_api_registry.go`) adds `tools_builtin.StepwiseBuiltins()` to the resolvable pool AND force-merges it via `apirun.MergeBaseline` (baseline-style) whenever `isStepwiseDef(agentDef)` — pool membership lets an explicit CSV entry resolve, force-merge means a restrictive CSV can never strip it. Because the gate lives inside `buildAPIRegistry`, all three callers (in-process api, api-via-cli, cli_interactive claude/codex over the `agent mcp` bridge) get it identically; a full-mode agent's tool catalogue never resolves it. `ToolEnv.NodeID`/`ToolEnv.Steps` are set alongside (`proc.nodeID`, `s` — `*Spawner` implements `apirun.StepSession`).

`Advance`'s four outcomes map to tool results (`complete_step_result.go`): **rejected** enumerates missing/invalid evidence, records a durable per-step counter (`repo.AgentStepCursorRepo.RecordRejection`, skipped for guard-miss reasons via `Rejection.CountsTowardEvidenceCap`) and force-fails via `failSession` at `service.StepRejectionCap`; **next** stamps a task-boundary (`env.Steps.NoteStepBoundary`) and returns `{step_id, revision, step_index, total, title, instruction, flags}`; **done** returns a final-completion instruction without itself signaling completion; **rotate** — the Advance transaction is already committed — calls `env.Steps.RequestStepRotation` and tells the agent to stop.

**The rotate chain.** `RequestStepRotation` is a non-blocking send on `Spawner.stepRotateCh` (mirrors `RequestRestart`/`nudgeRequestCh`), drained by `monitorAll`'s top-of-loop select into `dispatchStepRotation` (`step_rotation.go`) — all proc-field mutation stays on the monitorAll goroutine. `dispatchStepRotation` is `checkProactiveRestart`'s tail minus the idle/threshold gates (the decision was already made by `stepengine.ShouldRotate` inside `Advance`): `NoteProactiveRestart` + `proc.proactiveRotationPending=true` + `lowContextSaving=true` + a `doneCh` swap + `go s.initiateContextSaveProactive`. `initiateContextSaveProactive` → `contextSaveViaAgent` (stepwise skip, no context-saver spawn) → `finalStatus=CONTINUE` → `monitorAll`'s continuation branch calls `relaunchAndRegister`; `proactiveRotationPending` makes `applyProactiveRotationCarry` reset `restartCount` instead of incrementing it and bypasses `defaultMaxContinuations`, so a step rotation never burns the phase's continuation budget. The relaunch's prompt is rebuilt from the cursor via the existing `fetchPreviousDataAndReason` → `stepwiseResumeData` path — no new relaunch-prompt logic was needed.

### Lifecycle integration

`handleCompletion` (`completion.go`) runs `stepwiseCompletionGuard` (`completion_stepwise.go`) immediately before the whole-agent `validation_commands` block: for a stepwise def whose cursor (`stepengine.Engine.State`) is still short of its last step, it flips `result=pass` to `fail`/`result_reason=service.ResultReasonStepsIncomplete` and writes a `steps_incomplete` session finding (same shape/posture as `writeValidationFailureFinding` — nil-pool guard, log-and-continue) before validation ever runs, so an incomplete run never burns a 5-min-per-command pass. Per-step `checks` run inside `stepengine.Advance` itself via a real `stepengine.CheckRunner`: `complete_step` (`tools_builtin/complete_step.go`) wires `apirun.StepSession.RunStepChecks` (`Spawner.RunStepChecks`, `step_checks.go`) into `stepengine.New`, built only when `env.Steps != nil` so a nil `env.Steps` yields a nil (not typed-nil) `CheckRunner` and `Advance` skips checks entirely. `RunStepChecks` shares `runShellCommands` (`validation.go`, extracted from `runValidationCommands`) with whole-agent validation, but at a 60s-per-command timeout, an 8KB tail (embedded in the agent-facing `check_failed` rejection), and a 4-minute total budget — a budget expiry converts to a normal check failure rather than an opaque tool error, since `complete_step` arrives over the `agent mcp` bridge whose socket client has a 5-minute read deadline. Every relaunch reason (low-context, fail-restart, stall, rate-limit) reuses the same `(instance, node)` cursor key by construction: `relaunchForContinuation` passes `phase`/`oldProc.workflowInstanceID` straight through to `spawnSingle` → `prepareSpawn` → `snapshotStepCursor`, and none of `relaunchWithBookkeeping`'s session-keyed teardown (`DropProactiveRestartState`, `globalLedgerStore.drop`, `FinalizeSessionCost`, terminal-signal unregister) touches DB cursor state. The codex crash-resume path needs no stepwise branch either — `startOrResumeThread` swaps in the `crash-resume` injectable, and the resumed thread's history already holds the last `complete_step` tool result, so the new step_id/revision the agent needs is already in-thread.

## Validation Commands

When an agent finishes `result=pass`, `handleCompletion` runs `agent_definitions.validation_commands` (JSON array) sequentially via `sh -c` in `proc.workDir` (`runShellCommands`, `validation.go`); per-command timeout 5 min (`validationCommandTimeout`), env = full agent envelope minus `NRFLO_AGENT_TOKEN`/`NRF_SESSION_ID`, output tail-captured to 64 KB (`validationTailSize`). First non-zero exit flips result to `fail` (`result_reason=validation_failure`) and writes a `validation_failure` finding carried to the retry session by `copyFindingsForContinuation`. Stepwise per-step `checks` reuse `runShellCommands` at a 60s per-command timeout / 8KB tail / 4-minute total budget (`step_checks.go`) — see [Stepwise Prompt Assembly § Lifecycle integration](#lifecycle-integration) for that path and the `steps_incomplete` completion guard.

## One-Off Child Spawners

`delegate.go`, `consult_run.go` and `context_save.go` each build a short-lived child `Spawner` rather than reusing the parent, so anything the parent's `Config` carries must be re-supplied deliberately. Two things bite when they are not.

A wrapper that also wraps its spawn in its own context deadline must derive it via `SpawnDeadline` (`agent_timeout.go`): the definition `timeout` column is **minutes**, and open-coding it in seconds yields an outer deadline 60x under the child process budget `prepareSpawn` derives from that same value — the outer one wins and kills the child mid-turn.

Session hooks come from `childSessionHooks` (`spawner_session.go`), which composes the parent's `OnSessionRegister`/`OnSessionUnregister` with the child's own session-id capture. The parent callbacks are what place the session in the orchestrator's `sessionID→*Spawner` index (`runState.spawners`, or `auxSpawners` when no run loop owns it), and that index backs `ListTools`/`CallTool` for the MCP bridge plus `BumpLastMessage`/`SetLastMessage`/`TriggerIdleNudge`/`RequestTerminalSignal`. A child that writes its own `OnSessionRegister` and forgets to forward gets no error: `tools/list` returns `[]` and every `record-event` heartbeat resolves to no proc, so a working agent looks frozen and is killed every `stall_start_timeout_sec`. The forwarding also means registrations from *grandchildren* (a delegate worker's own nested fanout) bubble up through every composed hook: the capture callback receives the registering `*Spawner`, and a caller tracking its direct worker must compare it against the child Spawner it built (see `spawnDelegateWorker`/`runConsult`) or a grandchild registration overwrites the captured session id and the caller reads back the wrong session. Regression cover: `TestChildSessionHooks_*` (`spawner_session_test.go`).

## Delegate

`Spawner.Delegate` (`delegate.go`, implements `apirun.Delegator`) resolves the caller session → project/ticket/workflow instance (a fresh hidden `_delegate_host` instance, lazily seeded as a global `workflows` row, when the caller has none — console sessions); loads the tier's `system_agent_definitions` row (`extractor`→`_t2_extractor` haiku-4-5/low/read-only, `executor`→`_t1_executor` sonnet-5/medium/`tools=*`, migration `000182`). Recursion depth is per-chain and threaded in-memory down the spawn tree, never a shared DB counter: each worker's one-off child `Spawner` carries `Config.DelegateDepth+1`, and `buildAPIRegistry`'s check (`spawner_api_registry.go`, `service.DelegateMaxDepth`, default 2) strips `delegate` once `DelegateDepth+1` exceeds the cap — so a top-level spawner (depth 0) and every fresh top-level delegate call keep it, while a second-level worker loses it; `_t2_extractor`'s tools CSV also omits `delegate` natively. For each fanout item (default one) it builds a one-off child `Spawner` (mirrors `consult.go`) running a one-phase `_delegate` node under the resolved instance, `ExtraVars` `DELEGATE_BRIEF`/`DELEGATE_CONTEXT`/`DELEGATE_ITEM`, and returns immediately (`{"delegation_id","status":"running"}`) while the fanout spawns detached (`go s.runDelegateFanout`, `context.Background()` — the caller's tool ctx must not cancel it). `delegate_id` is `"<wfiID>.<rand>"`. Because each worker `Spawn` blocks until its agent completes, `trackDelegation` writes the `_delegation_<id>` finding (`workflow_instance` scope, key `wfiID`) TWICE: seeded `{tier, done:false}` synchronously before `Delegate` returns so `GetDelegation` resolves the delegation as `running` for the whole run (never "unknown delegation"), then rewritten `{tier, session_ids, spawn_errors, done:true}` after `wg.Wait` (`spawn_errors` is index-aligned with `session_ids`: the spawn error message for a worker whose slot is `""`, surfaced by `GetDelegation` as `worker failed to start: <reason>`). A hidden `_delegate_host` instance is marked `completed` at that point so run-less console callers don't leak `active` rows. `Spawner.GetDelegation` (`delegate_poll.go`) resolves `wfiID` back out of the delegation id, authorizes it against the caller's project, reads the tracking finding, reports `running` while `done` is false, and once done reads each worker session's terminal status + `_delegate_findings` session finding (read+deleted, mirrors `_consult_answer`); the tracking finding is then deleted and status resolves to `completed`/`failed`. Worker `callback` and `timeout` statuses map to terminal `failed` — nothing ever answers a delegate worker's callback (no coordinator), so treating it as running would wedge the delegation in `running` forever. Neither method blocks — `tools_builtin/delegate.go`'s `pollDelegation` owns the bounded, heartbeated `wait_sec` wait (max 240s) around repeated `GetDelegation` calls, identical in shape to `pollSubworkflow`. Broadcasts: `delegate.started` (fanout kickoff), `delegate.completed`/`delegate.failed` (fanout tracked / a worker's spawn failed). `_delegate`/`_delegate_host` are hidden from the v4 read model like `_consult` (underscore-prefixed node/workflow). Cap config: `service/delegate.go` (`delegate_max_fanout` default 20, `delegate_max_depth` default 2; project>global>default, cloned from `service/subworkflow.go`).

## Consult

`Spawner.Consult` (`consult.go`, implements `apirun.ConsultantSpawner`) lets an api-mode agent ask a named consultant inline: resolves the caller session's project/ticket/workflow instance, loads the consultant def scoped to that workflow (`loadAgentDefinition`), truncates the caller transcript, then calls the shared `runConsult`. `Spawner.ConsultHost` (`consult_host.go`) is the hidden-host counterpart for a caller with no bound workflow instance (a console session, reached via `orchestrator.APIConsultant` → `console.Deps.Consultant`): it has no single caller-known workflow to scope the lookup to, so it resolves `consultantID` via `repo.AgentDefinitionRepo.FindConsultant(projectID, consultantID)` — project-local `agent_definitions` rows win over the reserved `__global__` namespace — and runs with `Transcript=""` (a console chat has no `AgentSession`-backed message history to summarize).

Both funnel into `runConsult` (`consult_run.go`, takes a `consultRequest` bundling whichever fields the caller resolved): validates the def (`Consultant=true`, `ExecutionMode=api`), builds a one-off child `Spawner` running a one-phase `_consult` node (mirrors `delegate.go`'s per-fanout-item child), blocks until it completes, and reads back the `_consult_answer` session finding (read+deleted). Broadcasts `consult.started`/`answered`/`failed` carry `req.CallerSessionID` verbatim — empty for a host call, so a listener keying off it must treat empty as "no caller session" rather than a malformed event. `prepareSpawn` strips `consult` from a consultant's own toolset (recursion guard, unaffected by this split). `_consult` is hidden from the v4 read model.
